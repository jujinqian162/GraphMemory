# ISETrace LLM query authoring

`scripts/generate_isetrace_llm_queries.py` is an offline dataset-authoring utility. It is not a Prefect experiment stage. By default it scans all raw ISETrace trajectory shards, deterministically shuffles the complete trajectory population with seed 13, and authors queries from the first `--limit` trajectories. Train/dev/test assignment happens later at the trajectory level.

The authoring path is:

```text
complete raw ISETrace shards
  -> deterministic seed-13 trajectory shuffle
  -> first --limit trajectories
  -> deterministic task text with event handles
  -> LLM-authored query + exact evidence quotes
  -> append-only minimal authoring JSONL
  -> later trajectory-level train/dev/test split
```

`call_result` motifs remain excluded by default so generic tool receipts do not dominate the pool.

## Frozen authoring record

The authoring JSONL is intentionally small. Each line has exactly four fields:

```json
{
  "id": "query:...",
  "text": "[I1 | user_intent]\n...\n\n[A1 | tool_call | write]\n...\n\n[E1 | tool_output | write]\n...",
  "query": "Why did the first run fail, and what was corrected before retrying?",
  "gold": [
    {
      "source": "E2",
      "quote": "stopped because an unset shell variable was referenced"
    },
    {
      "source": "A3",
      "quote": "ALERT_COUNTS=${ALERT_COUNT:-0}"
    }
  ]
}
```

The fields have fixed meanings:

- `id` is a deterministic record identifier generated by the script;
- `text` is the human-readable authoring task, with stable event handles and source boundaries;
- `query` is a natural user memory question or concise Agent memory-search query;
- `gold` is one or more minimal exact quotes, each paired with the source handle that contains it.

`I*` handles identify user intents, `A*` handles identify complete ToolCall arguments, and `E*` handles identify complete ToolOutputs. Gold currently uses only `A*` and `E*`. These are authoring handles, not provenance node IDs or retrieval chunk IDs.

A quote need not be unique across the whole task. It must occur exactly once inside the event named by `source`. This prevents ambiguity when the same text appears in multiple events without exposing internal event IDs or character offsets.

This four-field contract is the durable dataset surface. Source coordinates, motif IDs, output-container IDs, dependency edges, model request metadata, token usage, and review state are not part of it.

## Downstream compilation

During benchmark preparation, the four-field file is combined with the pinned trajectory source. The compiler uniquely matches the handle-delimited task text to one trajectory, resolves every `A*`/`E*` source, and converts `{source, quote}` directly into:

```text
(event_id, json_pointer, char_start, char_end)
```

No compiled-gold sidecar is produced. Motif IDs, answer/support containers, dependency edges, model metadata, and review state are neither required nor reconstructed as gold. The raw API response cache, rejected-task log, and query-stratum metadata mapping are operational artifacts. Only the four-field JSONL is consumed as the authoring dataset; the stratum mapping supports audit and grouped reporting but is never a retrieval feature or relevance label.

Prompt v7 (`isetrace-query-author-v7-independent-memory-groups`) uses exact quotes while emitting the minimal authoring schema. This differs from v5, where exact offsets usually covered complete selected ToolOutputs. v5 artifacts must not be used as evidence that fact-level gold has been annotated.

## Prompt behavior

Each request contains independent task-local text, a deterministic writing-style instruction, and a natural-language `authoring_brief`. The brief converts the internal motif intent and focused sources into a memory need without exposing graph relations, motif IDs, answer/support roles, or dependency labels. The text includes the user intent and the complete ToolCall/ToolOutput sources selected for that authoring task.

The model writes either a question that a user could naturally ask a memory-enabled assistant later or a concise search query that an Agent could issue to memory. Tool traces are evidence sources rather than the subject of an execution audit. The prompt uses several syntactically diverse examples and explicitly discourages repeated openings such as `For the ...`.

The prompt favors substantive facts, causes, corrections, decisions, reuse, and outcomes. It rejects generic byte counts, exit codes, write receipts, and benchmark language. Paths, numbers, variable names, commands, providers, and error text remain valid only when a real user would naturally remember or search for them and they do not turn the query into a lexical restatement. Query length of 12--35 words is a soft writing target, not a local validation boundary.

By default, every authoring task requests two independent query/exact-gold groups. Each query chooses its own minimal answer evidence; the two gold sets may overlap, differ partly, or be completely different. Both records may remain in the formal benchmark when they ask for different facts, relationships, or memory needs. They must not be counted as independent trajectories, and they must not be mere synonymous rewrites.

Gold contains only answer-bearing facts. Intermediate call, output, or artifact nodes are not gold merely because a provenance route passes through them. A linked-recall query may state something the user already remembers and ask for a related result; only evidence required for the requested answer is gold. A multi-fact query instead labels each distinct fact needed to answer every part.

## Memory-query strata

Authoring tasks are deterministically interleaved toward an initial 30/50/20 mixture:

- `direct_recall` (30% target): one substantive fact or outcome, serving as the flat-retrieval control;
- `linked_recall` (50% target): the user remembers one part of an episode and asks for a related earlier source, later correction, reuse, decision, or outcome;
- `multi_fact_recall` (20% target): the complete answer needs distinct facts from multiple events.

The ratio is approximate for small trajectories or when one stratum lacks enough valid motif targets. Task selection remains deterministic under the seed. Report retrieval metrics separately for the three strata as well as overall; a graph method should help linked and multi-fact recall without requiring every realistic memory query to be multi-hop.

The stratum is authoring metadata, not gold and not a retrieval feature. It is omitted from the durable four-field record and written to the operational `.metadata.jsonl` file keyed by query ID.

## Runtime configuration

Create `.env` from `.env.example` and set:

```dotenv
MODEL_ID=...
API_KEY=...
BASE_URL=...
```

The script uses the OpenAI Responses protocol with strict JSON Schema, `store=false`, explicit `stream=false`, request-digest caching, bounded API retries, and bounded validation rewrites. Explicit non-streaming mode is required because some compatible gateways otherwise return Server-Sent Events rather than one JSON response. Changing the model, prompt, schema, or packet changes the scientific run identity. API routing is operational: the same model may resume through a different endpoint. Because the endpoint remains part of each request-cache digest, responses are never silently reused across endpoints.

## Inspect v7 packets without network access

```bash
uv run python scripts/generate_isetrace_llm_queries.py \
  --source data/isetrace/sample/trajectories-00000.sample.jsonl \
  --source-revision e40e04d41c04e4eb4bae181ebdd41b61c688081b \
  --output data/isetrace/query-authoring/v7-dry-run.jsonl \
  --limit 10 \
  --dry-run
```

This plans the first 10 seed-shuffled sample trajectories and writes `v7-dry-run.jsonl.packets.jsonl`. It does not read `.env` or call the network.

## Generate queries from 300 raw trajectories

The default `--source` is `data/isetrace/raw/trajectories`, where all eight raw shards are discovered in sorted filename order before the seed-13 shuffle:

```bash
uv run python scripts/generate_isetrace_llm_queries.py \
  --source-revision e40e04d41c04e4eb4bae181ebdd41b61c688081b \
  --output data/isetrace/query-authoring/isetrace-v7-raw.jsonl \
  --limit 300 \
  --api-retries 3 \
  --validation-retries 2 \
  --timeout 240
```

`--limit` counts shuffled raw trajectories, not tasks or accepted queries. The query count is intentionally variable because a trajectory may have fewer than two eligible tasks and the model or deterministic validator may reject a task. Defaults are `--per-trajectory 2`, `--tasks-per-call 2`, and `--queries-per-task 1`. The progress bar is trajectory-based and continuously displays the current accepted-query count.

Accepted records, metadata, rejections, and trajectory completion markers are appended and fsynced during the run. Reusing the same `--output` resumes the same run. For example, after completing `--limit 300`, rerunning with `--limit 3000` skips the completed first 300 shuffled trajectories and processes only the remaining 2700. `--limit` and `BASE_URL` are deliberately excluded from the scientific run identity; source digests, seed, prompt/model identity, and scientific authoring options must remain unchanged. Endpoint changes are recorded as append-only selection-index segments. Use a new output path when a scientific input, especially `MODEL_ID`, changes. Exhausting transport/API retries aborts the run before the active trajectory receives a completion marker, so a later invocation can safely retry it; semantic model rejections and local validation exhaustion remain ordinary per-task rejections.

Outputs:

- `isetrace-v7-raw.jsonl`: accepted four-field authoring records, appended one record at a time;
- `isetrace-v7-raw.jsonl.metadata.jsonl`: query-ID to task/trajectory/`memory_mode` mapping; experiment preparation requires this sidecar, includes its digest in scientific identity, and propagates `memory_mode` into prepared and per-task evaluation metadata;
- `isetrace-v7-raw.jsonl.rejected.jsonl`: model, validation, and trajectory-adaptation rejections;
- `isetrace-v7-raw.jsonl.progress.jsonl`: durable trajectory completion ledger used for resume;
- `isetrace-v7-raw.jsonl.run.json`: immutable scientific run identity used to reject incompatible resume attempts;
- `isetrace-v7-raw.jsonl.endpoint-history.jsonl`: append-only model/endpoint segments and their first shuffled selection index;
- `.isetrace-v7-raw-cache/`: raw Responses payloads keyed by complete request digest, including endpoint.

An existing legacy output without the new `.run.json`/`.progress.jsonl` sidecars is not resumed automatically; choose a new output path or remove the old artifacts first.

Local validation enforces only durable and auditable invariants: structured response shape, valid source handles, exact unique quote grounding, duplicate query rejection, and internal-ID leakage. Naturalness, the 12--35-word preference, substantive memory value, semantic evidence sufficiency, and non-redundancy remain prompt and review responsibilities.

Generated records are unreviewed candidates. Review state is deliberately not embedded in the four-field record. They are suitable for quality inspection and engineering runs, not formal result claims. Human review must verify query naturalness, answer sufficiency, quote minimality, whether every requested fact is actually entailed by the quoted spans, and whether two records from one task represent genuinely different memory needs.
